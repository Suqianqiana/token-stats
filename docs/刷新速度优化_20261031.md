# 刷新速度优化：实测、方案与结果（2026-10-31 第105轮）

> **结论：慢的不是商汤，是 WorkBuddy 会话扫描本身。**
> 优化前 WB 页刷新 **23~30 s**，优化后 **≈0.9~1.0 s**（活跃会话正在增长时也是 1 s 内）。
> 商汤走缓存只要 0.16 s，且刷新原本就**只刷当前页的数据源**——它从未拖累 WB 页。

---

## 一、实测数据（本机真实规模）

会话 jsonl **687 个文件 / 合计 1957 MB**；增量游标 `cache.json` 13.85 MB（68573 条条目）。

| 阶段 | 优化前 | 优化后 | 说明 |
|---|---:|---:|---|
| 载入 `cache.json` | 0.58 s | 0.17 s | 体积 13.85 → 9.6 MB |
| 枚举 + stat 全量 | 1.29 s | 0.45 s | 687 个文件 |
| 副本去重 `_dedupe_files` | **8.0 s** | ~0 s（稳态） | 结论缓存化 |
| 解析"已变化"文件 | **~13~15 s** | ~0.05 s | 5 个文件 175 MB → 只读尾部 |
| 重放缓存条目（~68.7k 条） | ~0.5 s | ~0.3 s | 紧凑 list，免去 key 查找 |
| 写回 `cache.json` | **3.46 s** | 0 s（无变化）/ ~0.15 s | 无变化不写 + C 编码器 |
| **合计（WB 页）** | **23~30 s** | **0.9~1.0 s** | |

对照：`load_dsh_stats()` 0.51 s；商汤 0.16 s（冷路径 14 s）；
`scan_full(force=True)` 全量重扫 126 s（只在缓存丢失时发生）。

### 慢在哪：三个根因

1. **增量是假增量**：判据 `sig = "{mtime_ns}:{size}"` 精确相等，**文件动一下就整个文件重读**。
   而正在聊的会话文件已经 **101 MB**，第二个 57.6 MB —— 每次刷新要重读 **175 MB**，
   会话越大越慢（这就是"越用越慢"）。
2. **副本去重 8 s 只服务一个没人看的字段**：`_dedupe_files` 算出 `dropped_files` 只喂给
   `dupFilesDropped`（UI 从未显示）；真正参与统计的是"全文件扫描 + 消息级去重"。
3. **切页 = 一次全量扫描**：`_switch_nav()` → `load_initial()` → 100 ms 后 `refresh()`，
   所以在 WB / DSH / 多机之间来回切一次，就要重新扫一遍。

## 二、四项优化（已全部落地）

### 优化 1：真正的尾部增量（主打，`scanner.scan_full`）

缓存条目新增 `off`（已消费到的**字节**偏移）、`hd`（首部指纹）、`hl`（指纹覆盖的长度）：

| 文件状态 | 处理 |
|---|---|
| `sig` 未变 | 直接重放缓存条目 |
| 变大 且 首部指纹未变 | **从 `off` seek，只解析新增尾部** |
| 变小 / 首部被重写 | 全量重读（正确性优先） |

要点：
- **二进制读**（`open(path,"rb")`）。文本模式的 `tell()` 是"不透明 cookie"，只有字节偏移才能安全 seek。
- **半行保护**：只有以 `\n` 结尾的行才推进 `off`；续读时若第一行不以 `{` 开头（上次的残留半行）就丢弃。
- **指纹长度随文件大小**（`hl = min(8KB, size)`）。踩过的坑：短文件按固定 8 KB 算指纹，
  一追加就会读到新内容 → 指纹永远不匹配 → 尾部增量永不命中（合成用例第一条就红了）。

### 优化 2：缓存体积与写盘

1. 条目从 dict 改成**紧凑定长 list** `[d,m,i,o,t,c,r,s,mid,ts]`：13.85 → 9.6 MB；
2. 落盘用 `json.dumps`（C 编码器）+ `write`，不用 `json.dump`（iterencode 走 Python 层）：
   9.6 MB 实测 **0.83 s → 0.13 s**；
3. **无变化就不写**（`dirty` 标记）：空闲时的自动刷新 0 写盘开销。

### 优化 3：副本去重结论缓存

`__dup__ = {"sig": 文件集合+首部指纹汇总 md5, "dropped": [...]}`，签名不变就直接复用。
签名只取 `(路径, 首部指纹)`——**刻意不含 size**，否则活跃会话每长一点就失效，等于没缓存。
首次运行 / 出现新会话文件 / 首部被重写时重算一次（约 8 s），届时才慢。

### 优化 4：切页不再白等（`card_app`）

1. `load_initial()`：距上次刷新 **< 60 s** 就直接复用快照渲染，**不触发扫描**（手动点刷新照扫）；
2. `_auto_refresh_tick()`：窗口不可见 / 最小化时跳过（对着看不见的窗口读几百 MB 没意义）；
3. 副标题逻辑抽成 `_set_source_subtitle()`，复用快照时也能修正文案；
4. 商汤保持独立：只在商汤页拉，300 s TTL + 事件缓存，失败不影响其它页。

## 四、口径不变性验证（提速有没有动到"去重 / 精准统计"）

用一个独立脚本 `tools/check_refresh_equiv.py` 把**提速前的 scanner.py（git `ee26e0c`）**拉出来，
和同一份数据上的新版**逐字段对账**（比对 `entriesTotal / models / daily / sessionsTotal /
dailySessions / dupFilesDropped / dupFilesTotal / today / firstDay / lastDay`）：

| 断言 | 数据 | 结果 |
|---|---|---|
| A. 老版全量 == 新版全量 | 真实会话 473 个文件 / 137 MB（1 MB 以下全量冻结） | ✅ 条目 5609 完全一致 |
| B. 缓存重放 == 全量 | 同上（第二轮全命中缓存） | ✅ |
| C. 追加 2 条后 增量 == 全量 | 同上 | ✅ 条目 5609 → 5611，`filesAppended=1`（确认走的是尾部） |
| D. 截断重写后 增量 == 全量 | 同上 | ✅ 回退全量路径正确 |
| E. 历史副本场景 老版 == 新版 | 合成夹具：两账号轮换 / sid 被改的副本 / 无 sid 文件 | ✅ |
| E2. 共享历史只计一次 | 同上（6+4+1+1 = 12 条） | ✅ |
| E3. 副本识别仍生效 | 同上（Jaccard ≥ 0.6 → 各丢一份） | ✅ dropped=2 |
| E5. 两账号轮换的两份都保留 | 同上（A↔B 只有 4/10 = 0.40，**不该**判成同源） | ✅ 第70轮口径未变 |

结论：**提速只改了"怎么读文件"和"什么时候重算"，没有改"怎么算"。**
另外原回归里的去重相关断言（第67~70轮的副本判据、消息级去重、`mid` 必存等 30+ 条）在
533 项里全部保持绿色。

⚠️ 写夹具时踩过一个坑（记下来免得下次重踩）：`_msg_id_sample` 用的正则是 `"id":"…{6,}"`，
**消息 id 短于 6 字符根本不会被采样** → 副本识别永不触发。夹具报"没去重"时先看这个，
别急着怀疑代码。
